# Agent Note: 将 web fetch 连接固定到已验证的公开地址

Status: implemented

[English](2026-08-28-web-fetch-public-network-pinning.md) | 中文

## 问题

`web_fetch` 接受任意 HTTP(S) URL，并把 DNS 与连接建立交给平台 `fetch`。协议、凭据、大小、超时和重定向检查无法阻止模型提供的主机名解析到回环、链路本地元数据、私有服务或其他特殊用途地址。即使先解析并验证主机名，再调用普通 `fetch`，传输层仍可能再次解析该名称，因此仍存在 DNS rebinding 的竞态。

同源重定向需要与初始请求相同的保护。主机名可以在第一跳返回公开地址，在下一跳返回私有地址，而 URL origin 不发生变化。

## 决策

`@deepseek-ai/dsh-web-fetch-http` 仅允许公开网络目的地，并在 URL 解析、DNS 解析和连接建立三个阶段执行该决策。

URL 检查在 WHATWG 规范化后拒绝 localhost 名称和非公开 IP 字面量，包括十进制、八进制、十六进制、缩短 IPv4、IPv4 映射 IPv6、过渡前缀，以及私有或特殊用途范围。主机名解析会取得所有答案；只要包含一个非公开或格式错误的答案，就整体拒绝该目的地，而不是选择其中的公开地址。

每个请求跳创建一个新的 Undici dispatcher，其 connector lookup 只返回已验证的地址集合。原始主机名继续用于 HTTP Host 和 TLS 验证，但 socket 创建不能再次查询 DNS 或连接到其他地址。只有在响应正文读取或取消后才释放 dispatcher。每个允许的同源重定向都会重新执行 URL 验证、DNS 验证和 dispatcher 创建。

匿名提供方没有私有网络旁路。确实需要访问 intranet 时，应使用具有明确权限的独立连接器。

## 曾考虑的替代方案

**阻止可疑的主机名前缀。** 否决，因为替代字面量形式、任意 DNS 名称、IPv6 和 rebinding 都能绕过字符串检查。

**先解析并验证，然后正常调用平台 `fetch`。** 否决，因为连接建立会再次查询 DNS，留下检查时与使用时不一致的缺口。

**从混合 DNS 结果中丢弃私有地址并使用公开地址。** 否决，因为攻击者控制答案的顺序和轮换；整体拒绝才能形成稳定的安全决策。

**提供允许私有网络的配置开关。** 否决，因为该提供方是匿名公开 Web 实现。旁路会悄然把广泛可用的模型工具重新变成内部网络请求原语。

## 后果

`WEB_BLOCKED_URL` 同时覆盖字面量和 DNS 派生的非公开目的地，并且不泄露解析出的私有地址。公开站点继续通过 Undici 保留 HTTP 状态、重定向、解码、超时、abort 和大小限制行为。

测试固定替代 IPv4 形式、IPv4/IPv6 特殊范围、混合 DNS 结果、格式错误的答案、connector 地址固定、逐跳 rebinding 拒绝、dispatcher 清理，以及该包原有的传输行为。该策略有意保持保守：回环、私有、文档、基准测试、过渡或保留网络的工作流需要另一个具有权限的能力。

因此，无密钥 ACP web-fetch 快照会显式选择一个独立的测试专用提供方，并且只接受其精确的 loopback fixture URL。它仍会演练真实的模型侧 fetch 工具与 Markdown 渲染，同时不会给生产提供方增加私网绕过能力。
