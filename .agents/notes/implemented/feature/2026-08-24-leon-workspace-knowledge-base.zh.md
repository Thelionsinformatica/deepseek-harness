# Agent Note: Leon 工作区知识库

Status: implemented

[English](2026-08-24-leon-workspace-knowledge-base.md) | 中文

## 问题

Leon 需要一种持久的文档知识：它应在模型切换和会话压缩后继续存在，同时不能把个人记忆变成文档堆。有效回答必须能追溯到进入项目的原始字节；当来源变化或两个来源相互冲突时，生成的摘要和关系还必须可以修复。

把所有文档正文交给 `memory_remember` 会抹掉这种区分，并让来源、冲突处理和完整性检查变成隐式行为。在尚未观察到检索失败之前安装向量数据库，则会增加服务和迁移面，却不能证明语义检索确有必要。

## 决策

发布的 Leon preset 包含按需加载的 `leon-knowledge-base` Skill。它在每个工作区的 `.leon/knowledge/` 下创建一套明确的知识库，并与个人 `memory_*` 记录分离：

- `raw/` 保存不可变、按内容寻址的来源副本。
- `wiki/` 保存生成的来源、概念、实体、比较和综合页面。
- `index.md` 是查询的第一入口。
- `schema.yml` 记录格式与写入规则。
- `log.md` 是仅追加的操作历史。

Skill 中的确定性辅助程序 `scripts/knowledge.mjs` 负责初始化、摄取、状态和 lint。摄取只接受活动工作区内的普通文件，拒绝自身生成目录和疑似凭据文件，将单个来源限制为 25 MB，以完整 SHA-256 命名并复制原始字节，然后创建待综合的来源页面。相同内容的重复摄取具有幂等性。Lint 会重新计算来源哈希，检查必需元数据、索引和日志成员关系，并验证 wiki 链接。

模型按照 Skill 指令负责综合。它把来源内容视为不可信数据，绝不编辑 `raw/`，让持久 wiki 断言以来源页面为依据，记录分歧而不是静默选择其中一个版本，并在回答重要断言前对照原始来源。PDF 和其他二进制文件可以被保存，但综合需要兼容的读取器或提取后的文本来源。

该能力采用作用域 Skill，而不是新的存储 provider。当前消费者是 Leon agent 工作流，当前 provider 是项目文件系统；在没有第二种实现时，把它拆成 service、provider 和 consumer package 只会产生空抽象。当出现第二种存储后端、非 agent 消费者或经测量确认的检索规模需求时，provider 接缝才成立。

## 验证

聚焦的辅助程序测试覆盖可重复初始化、基于哈希的不可变摄取、重复处理、工作区包含约束、敏感来源拒绝、状态计数、原始来源篡改检测以及损坏的 wiki 链接。Leon preset 集成测试证明该 Skill 仅属于 Leon，并能通过真实 `skill` 工具加载。加载器快照通过发布组合固定模型可见的目录条目和完整加载指令。

## 考虑过的替代方案

**把文档存入个人记忆**——拒绝，因为这会把用户偏好和个人事实与外部来源材料混合，并丢失可审计的事实来源边界。

**立即安装 embedding、向量数据库或 Letta**——V1 拒绝。初始工作流可通过索引和文本搜索检索，而原始来源与 Markdown 保持可移植。后续检索评估可以证明语义搜索是否值得其运维成本。

**只发布文字指令而不提供确定性辅助程序**——拒绝，因为路径包含、按内容寻址的副本、大小限制、幂等性和完整性 lint 不能依赖模型是否遵守指令。

**现在创建专用存储 package**——拒绝，因为目前只有一个 provider 和一个 consumer。仓库的 service/provider/consumer 模式适用于真实可替换性，而不是推测性的结构。

## 后果

Leon 获得可移植的项目知识，其证据能在本地模型和 API 模型之间切换时继续存在。在任务真正需要完整工作流之前，加载 Skill 只增加简短的目录描述，并且没有后台 watcher 或云服务接收项目数据。

V1 有意不包含自动目录 watcher、PDF 提取管线、embedding、reranker、Web 界面或后台整合。用户或 agent 明确摄取来源并运行 lint。这使来源与成本可预测，但大型或命名较弱的集合以后可能需要经过测量的检索改进，以及晋升后的 provider 边界。
