# Agent Note: Repeated tool failure recovery policy

Status: implemented

[English](2026-08-24-tool-failure-recovery-policy.md) | 中文

## 问题

工具错误会以带日志记录的 `tool/result` 返回给模型，但此前没有确定性机制阻止模型再次提交完全相同的失败调用。只依赖供应商模型的推理并不可靠：重复的 shell、文件系统或浏览器失败可能持续消耗时间和 token，却不产生新证据。已有重复工具提醒是建议性的，并且原本不区分调用结果；让它同时负责失败，要么力度不足，要么会与更强的恢复策略产生重叠消息。

## 决策

在基础 bundle 和 ACP 示例中交付 `@deepseek-ai/dsh-failure-recovery-policy`，配置 `maxEquivalentFailures: 2`。插件按活跃 agent 观察顶层模型请求的调用，匹配精确工具名、规范参数和等价的最终失败身份。第二次等价失败后，它通过 `additionalContexts` 注入一条紧凑且带来源的恢复提示；正常 agent loop 会把该提示记录为 `user/message`。如果下一次请求仍是完全相同的调用，单调 `ctx.tools.guard()` 会在工具实现执行前拒绝它。

锁定不会阻碍进展：更换工具、修改参数、出现不同失败、调用成功或收到新的用户提示都会开始新链。直接工具调用和嵌套 Code Mode 调用不在策略范围内。原始参数和非结构化错误消息保留在已有审计工具结果中，不会复制到恢复指导。被拒绝的 token 会从观察中移除，因此 guard 不会形成不断增长的自我拒绝链。

基础 bundle 现在为所有主机模式统一拥有 JSON 存储中心及领域形式。策略把每个会话的链存入一条经过 schema 验证的恢复记录；领域的逐记录原子变更会串行化并发完成，并在主机或会话恢复后重新提供该记录。恢复键不包含供应商／模型身份，因此自适应路由不能清除该链。

本包还发布由代码拥有的 `ToolPolicy`、结构化 `InvocationOutcome`、不可变 `RecoveryEvent` 和 `AtomicRecoveryStore` 接口。持久实现与内存实现都会按事件 id 去重，并签发带 TTL 和单调 fencing token 的租约。这些约定使具有外部效果的适配器能加入幂等及不确定结果协调，而不会让模型控制效果或重试分类；精确失败 guard 尚不会为每次调用自动预留租约。

`repeat-tool-reminder` 现在只跟踪成功调用。失败或被下游阻止的调用会重置其建议链，使每类结果只有一个所有者和一种消息。

## 验证

聚焦集成测试挂载生产 agent loop、工具服务、存储领域、模拟模型适配器和两个 guard 插件。测试证明：两次等价失败后出现提示、第三次分发前被拒绝、下游上下文得以保留、按 agent 隔离、成功及用户输入会重置、改变调用后可恢复、通配符排除、直接调用排除、嵌套调用排除，以及不会产生重复的成功调用提醒。原子存储测试证明并发失败递增、重放去重、持久重新打开、独占租约所有权、过期接管及旧 fencing token 拒绝。交付的 ACP 组合快照执行真实失败工具序列，并固定带日志的恢复上下文和拒绝结果。

## 考虑过的替代方案

**强制隐藏或可见的思维链步骤** — 拒绝。恢复机制要求改变可观察策略，而不要求公开私有推理，也不向审计轨迹添加无法验证的文字。

**把现有建议提醒改成成功／失败混合策略** — 拒绝。成功的幂等轮询与等价失败需要不同的升级语义；独立插件使配置和所有权保持清晰。

**阻止第二次失败尝试** — 拒绝。一次重试可能对瞬态错误有用。系统观察并记录第二次等价失败，只拒绝之后仍未改变的分发。

**对参数或错误使用模糊匹配** — 在出现需求证据前拒绝。精确规范身份可预测，允许有意的参数变化，并避免对合理重试产生误报。

## 后果

Leon 现在能确定性终止一种常见的无进展循环，同时保留完整原始结果用于审计和模型上下文。基础策略在达到阈值前不消耗模型 token，之后只增加一条紧凑的追加消息。它不改变模型路由、供应商故障转移或传输重试。

精确失败链通过已配置的领域后端跨重启及会话恢复保留。同一并行批次中已经准入的调用可能在累计失败生效前完成，但它们的完成会被串行化，不会丢失计数。JSON 后端只协调一个主机进程；跨进程分发协调仍属于后端能力，而不是本实现的保证。
