# Agent Note: 保留缓存请求前缀的增量压缩

Status: implemented

[English](2026-10-30-incremental-compaction-strategy.md) | 中文

## 问题

基础压缩后端过去每次压缩都把整个可选范围折叠成一条检查点，因此每次压缩都会重写模型请求的最早部分，提供方需要重新读取该前缀，提示词缓存从新检查点重新开始。长会话——该后端所针对的部署形态——过去每次压缩都要支付这次前缀重写，而不是只支付一次。

## 决定

[`compaction-basic`](../../../../packages/compaction/compaction-basic/README.zh.md) 新增可选的 `strategy: incremental`。范围选择从最新保留检查点之后开始，而不是从首个表面消息开始，因此一次压缩只折叠该检查点之后到达的消息。更早的检查点保持位置与文本不变，请求前缀以它们结尾并在多次压缩之间逐字节一致，只有新折叠的范围会使缓存状态失效。

检查点深度由 `maxGenerations`（默认 8）限制。当保留检查点达到上限时，下一次选择回退到完整累积范围，把整条链折叠成一条检查点并开始新的一代。罕见的重置只需支付过去每次压缩都要支付的前缀重写；没有上限时，摘要 token 会无界累积。

自动压力压缩与 `/compact` 都会把解析后的策略传入范围选择。显式范围的 `compactRegion` 调用者不受影响：范围由它们自己给出。默认仍为 `cumulative`，因此已交付的配置保持其历史形态，该变更是按组合选择启用的。

## 考虑过的替代方案

**把增量设为默认。** 否决：这会改变每个既有配置的历史形态，保留多条摘要而不是一条，并且在相同压力下可能需要更多压缩尝试。本仓库的默认值需要证据支撑，因此该特性通过显式字段交付。

**把字段加入按模型策略表。** 暂时否决：策略描述部署如何读取历史，而不是某个模型路由能承担多少；按路由拆分会让一个会话出现两种不兼容的历史形态。

**发布独立提供方包。** 否决：事务、配对、稳定性、摘要与持久化机制已在本包中存在，为一个选择规则而复制它们会让后端的正确性义务分叉。

**把摘要无上限地折叠进摘要。** 否决：检查点 token 会在请求中单调增长且没有强制重置，请求最终会失去该策略本应带来的节省。

## 后果

- 增量压缩每次释放的 token 少于累积压缩；较紧的 `thresholdRatio` 可能需要更高的 `compactionRetries` 才能清除压力。
- 表面上最多保留 `maxGenerations` 条检查点消息；它们的合计 token 相对其替换的原始范围很小，但并非免费。
- 达到上限时的新代重置是唯一会重写前缀的增量路径，每 `maxGenerations` 次压缩发生一次。
- 恢复的会话沿用其配置当前解析出的策略；已写入的历史对两种策略都可读。

## 验证

- `vitest run packages/compaction/compaction-basic`——176 个测试，其中 7 个新增测试覆盖最新检查点之后的选择、首个检查点之前回退、无新内容时拒绝、达到代数上限时回退、配置校验，以及一次引擎运行：第二次摘要只包含检查点之后的消息，而首个检查点仍在表面上。
- `pnpm run typecheck`、`pnpm run build` 与 `pnpm run lint` 覆盖改变的包表面。
- 生成的配置目录记录 `strategy` 与 `maxGenerations`；包 README 配对记录该行为、缓存影响与重试注意事项。
