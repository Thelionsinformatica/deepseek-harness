# 记忆 V2 — 搜索与检索

[English](memory-v2-retrieval.md) | 中文

## 目标

提供稳健、可审计且本地优先的检索，从现有词法搜索开始，逐步演进为本地混合检索。

## 检索层

1. **精确匹配**
   - 对精确 token 执行确定性匹配。
2. **词法搜索（始终启用）**
   - `memory-local` 会规范化词项并评分，同时继续充当确定性回退路径。
3. **本地语义搜索（已实现、需显式启用）**
   - 通过回环地址上的 Ollama embedding 端点使用 `nomic-embed-text:latest`。
   - 在任何候选文本到达 Ollama 之前，先执行 workspace 过滤。
   - 使用有界的进程内文档向量缓存和混合重排序，在不修改持久 schema 的前提下增加同义召回。
   - 超时、传输、验证和响应大小错误都会回退到词法检索。
4. **确定性最终排序（Leon preset 始终启用）**
   - 验证精确 workspace 所有权、提供方输出、时间谱系与活动有效性；删除重复 id，并限制面向模型的结果。
   - 规范化提供方相关性占 55%，以 30 天为半衰期的指数新近程度占 20%，importance 占 15%，确认类别与 confidence 占 10%。
   - 旧记录使用中性值，相同分数依次按分数、更新时间和 id 决胜。
5. **业务过滤器**
   - `workspaceId`、时间有效性、替代关系、过期与 `sensitivity`。
6. **审计历史（仅显式）**
   - `includeHistory`/`include_history` 会保留通过验证的非活动修订，并按 id 加 revision 去重。
   - 审计检索使用词法搜索，绝不会进入自动回忆或语义索引。

## 建议管线

1. 根据用户消息构建查询。
2. 应用强制工作区过滤器。
3. 每次都执行字面与词法搜索。
4. 仅当本地语义搜索已启用、可用且超过配置的最低分数时才执行。
5. 验证时间谱系，并按 `id` 合并、去重活动结果。
6. 对显式搜索与自动回忆应用共享最终分数。
7. 根据策略、项目数量与字符预算限制结果。
8. 在 `MemoryContextComposer` 中公开检索原因；只有审计请求才使用显式历史。

## 上下文控制

- 使用有界上下文字符串，例如初始流程中的 1,000–3,000 个 token。
- 排除无效记忆：已过期、已被取代或 `status != active`。
- 当纠正被安排在未来生效时，在新的 `validFrom` 时刻之前继续使用先前修订。
- 绝不把记忆转换为指令；将其呈现为非特权上下文部分。

## 最低指标

- 查询命中率。
- 有效回忆率：结果在下一轮中被使用。
- 按类别统计的 Recall@k 与人工精度。
- 以毫秒计的查询 p95 延迟。
- 敏感数据误报率。
- 组合后每个会话减少的 token 数量。
- 通过不含正文的 `memory/semantic-search` 事件统计冷启动与预热批次延迟、缓存命中数、嵌入文档数和词法回退率。

## 搜索迁移

- 阶段 1：保持词法搜索为默认值，在收益未经证明时不阻塞发布。
- 阶段 2：已经实现，但交付配置保持 `semanticSearch.enabled: false`；只有当 LEON-EVAL-PTBR 证明召回收益超过冷启动、延迟和本地资源成本时才启用。

## 当前运维基线

- 默认语义维度：256。
- 每次查询在 workspace 过滤后最多处理 200 条候选。
- 最多缓存 2,000 条文档向量。
- 在 Leon 开发机上以 8 个输入测得：模型冷启动后约 7.7 秒，随后 4 次预热运行耗时 68.5–107.4 毫秒。
- 可立即回滚：设置 `semanticSearch.enabled: false`；词法检索继续工作，且不需要迁移任何记忆。
- 最终排序可以独立回滚：设置 `tool-memory.ranking.enabled: false`，即可保留已验证的提供方分数顺序，同时不禁用检索或删除元数据。
- 时间历史可以独立回滚：设置 `memory-local.historyMode: v1`，新的纠正将采用原位覆盖；已有 V2 值仍可读取。
